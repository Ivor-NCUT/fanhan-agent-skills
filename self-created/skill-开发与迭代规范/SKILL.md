# Skill 开发与迭代规范

## 目标

把复杂 Agent skill 当成一个真实软件项目来开发：先澄清需求，再定义最小版本，最后用 GitHub 管理变更、评审和同步。这个 skill 的产出不是一次性的提示词，而是一套能长期维护的项目资产。

## 启动检查

开始任何 skill 开发或迭代前，先做四件事：

1. 阅读当前项目的 `README.md`、`AGENTS.md`、已有 `SKILL.md`、`各阶段的需求描述/` 和最近的 Git 状态。
2. 核对本地目录是否已经是 Git 仓库，远程仓库是否存在，当前分支是否和远程同步。
3. 如果任务涉及多人或多个 Agent 窗口协作，遵循“一个任务、一个 issue、一个 branch、一个 PR”的工作方式。
4. 如果用户给的是新需求，不直接开写完整实现，先进入单问题澄清。

## 单问题澄清

当用户提出需求后，每次只问一个关键问题。问题要服务于缩小实现范围，而不是泛泛收集背景。

优先问题顺序：

1. 这个需求解决的真实使用场景是什么？
2. 用户希望第一次可用版本具体做到哪一步？
3. 输入来自哪里，输出交付到哪里？
4. 哪些能力必须现在做，哪些可以后续再做？
5. 有没有不能破坏的既有流程、文档、仓库或数据？

当答案足以定义最小可用版本时停止追问，进入规划。不要为了追求完整感继续问一串问题。

## 最小版本规划

规划时用工程视角收敛需求：

- 先解决真实问题，再考虑漂亮架构。
- 优先让数据结构表达流程，少堆特殊分支。
- 先做能运行、能验证、能交付的版本。
- 不提前引入复杂插件化、通用框架或过度抽象。
- 保持已有 skill、脚本、文档和外部接口兼容，除非用户明确接受破坏性变更。

规划必须写入 `各阶段的需求描述/`，文件名使用：

```text
YYYY-MM-DD-NN-需求短名.md
```

每份阶段需求文档使用这个结构：

```markdown
# [阶段名称]

## 背景
[为什么要做]

## 用户需求
[用户原始诉求的整理，不添加未经确认的猜测]

## 已澄清信息
- [确认过的事实]

## 最小版本
- [本阶段必须实现的能力]

## 暂不做
- [明确推迟的能力]

## 设计取舍
- [为什么这样拆，为什么不做更复杂方案]

## 影响范围
- [会改哪些 skill、脚本、文档、配置或仓库流程]

## 验收标准
- [用户和 Agent 都能检查的完成条件]

## GitHub 工作流
- Issue: [待创建或已创建]
- Branch: [待创建或已创建]
- PR: [待创建或已创建]
```

## GitHub 协作规范

把 `main` 视为正式版本。每个实现任务都要有清楚边界：

- Issue 是任务卡，写目标、范围、非目标和验收标准。
- Branch 是独立工作线，命名为 `codex/<issue-number>-short-name`。
- Commit 是保存点，只提交同一件事相关的源代码、测试、文档和配置。
- PR 是合并前的检查窗口，默认由用户确认后再合并。

开始任务前：

1. 同步 `main`。
2. 创建或识别 issue。
3. 从最新 `main` 创建任务分支。
4. 明确本次 Agent 负责的文件范围和不应提交的生成物。

结束任务前：

1. 检查未提交文件和未跟踪文件。
2. 运行最小有效验证。
3. 确认没有把私密资料、临时导出、日志、缓存、候选人资料或 token 提交进仓库。
4. 推送分支并创建 PR，停止在 PR 阶段，除非用户明确要求合并。

## Skill 产物规范

复杂 skill 项目至少包含：

```text
skill-name/
├── SKILL.md
├── references/
├── scripts/
└── assets/
```

只有确实需要时才创建 `references/`、`scripts/` 或 `assets/`。如果 `SKILL.md` 接近 500 行，优先把长参考材料拆到 `references/`，并在主文件里写清什么时候读取。

## 测试与评审

当 skill 初稿或重要迭代完成后，创建真实测试提示：

- 保存到 `evals/evals.json`。
- 覆盖常见场景、边界场景和容易误触发的近似场景。
- 如果有可客观判断的结果，补充可量化检查。
- 如果主要是主观质量，优先让用户看真实输出，不强行写僵硬指标。

在支持评审工具的环境中，使用 skill creator 的评审流程生成可视化 review 页面；如果环境不支持，就在对话中逐项展示测试输入、输出和待反馈点。

## 交付回复

完成一次开发或迭代后，用简短中文说明：

```markdown
已完成：[一句话说明]

改动位置：
- [路径]：[做了什么]

验证：
- [运行过什么，结果如何]

下一步：
- [只给一个最关键问题或动作]
```

如果信息还不够，不要假装完成规划。只问一个最关键的问题。
