# 多维表格搭建咨询@泛函

## 目标

当用户想搭建一套比较复杂的飞书多维表格，但还没有清晰思路时，用咨询式单问单答把需求梳理清楚，最后输出一份本地 Markdown PRD。

这个 skill 不是直接替用户拍脑袋设计字段。它的价值是把用户脑子里的业务目标、操作流程、角色权限、数据对象、字段关系和看板指标逐步问出来，再整理成可执行的搭建说明。

它必须适用于任意业务域。公司经营管理、直播电商、CRM、招聘、库存、课程、活动、内容生产、服务交付、知识库、设备资产、财务台账都只是可套用的场景，不是默认场景。

## 适用场景

使用本 skill 处理这些请求：

- 用户要搭建飞书多维表格、Base、业务管理系统、台账、资源库或数据看板。
- 用户不确定应该建几张表、每张表有哪些字段、字段之间怎么关联。
- 用户要设计角色视图、管理者总览、业务看板或数据可视化模块。
- 用户希望通过多轮对话慢慢梳理需求。
- 用户明确说“一个个问题问我”“我一个个回答”“聊清楚后写 PRD”。
- 用户最后希望沉淀成 Markdown 文件、PRD、搭建说明或交给团队执行的文档。

如果用户只是要你直接创建一个简单表格、导入 CSV、修改已有字段，不需要使用完整咨询流程，除非他明显没有想清楚系统结构。

## 关键原则

### 每次只问一个问题

整个澄清阶段始终一次只问一个问题。不要一次列 5-10 个问题让用户填表。

每次用户回答后：

1. 先用 1-3 句话确认你理解到的结论。
2. 把这个结论纳入“已确认需求”。
3. 再问下一个最关键的问题。

如果用户一次回答了多个点，先吸收全部信息，再继续问当前最影响结构设计的一个问题。

### 先定边界，再定表结构

不要一上来问字段。按这个顺序推进：

1. 系统要支持什么业务目标和决策。
2. 系统覆盖哪些业务模块、流程或场景。
3. 使用者和权限角色是谁。
4. 核心数据对象有哪些，哪些已存在、哪些要新建。
5. 每个数据对象应该放在一个 Base、多个 Base，还是同一 Base 的多张表里。
6. 每个 Base / 表的定位和边界。
7. 每张表的字段、字段类型和状态选项。
8. 表之间如何关联、引用、汇总。
9. 不同角色的视图、待办、审批或看板怎么设计。
10. 仪表盘展示哪些指标，指标从哪里计算。
11. 最后写成本地 Markdown PRD。

### 尊重已有系统

如果用户说某张表或某个 Base 已经搭好了，不要重新设计它。只确认它需要向新系统输出哪些指标、是否需要关联或嵌入。

如果用户中途改变输出形式，例如从飞书文档改成本地 Markdown，立即切换交付面，不纠缠之前的方案。

### 字段设计要可落地

字段建议必须包含：

- 字段名
- 字段类型建议
- 字段用途或说明
- 必要时给出状态选项、公式或汇总逻辑

不要只写抽象概念，比如“数据字段”“业务信息”。要写到用户能照着在飞书多维表格里建字段。

### 不要被某个行业样例绑死

如果用户没有提到公司、部门、老板、客户、服务商、薪资、考勤，就不要主动把这些概念带入。

根据用户的业务域替换语言：

- CRM：线索、客户、联系人、商机、合同、回款、跟进记录。
- 招聘：岗位、候选人、面试、offer、入职、招聘渠道。
- 库存：商品 / 物料、供应商、入库、出库、库存、盘点、损耗。
- 课程：课程、学员、班级、课节、作业、学习进度、交付记录。
- 内容：选题、素材、脚本、拍摄、剪辑、发布、数据复盘。
- 活动：活动、报名、嘉宾、场地、物料、执行任务、复盘。
- 资产：设备、领用、归还、维修、折旧、责任人。

### 任务视图不要过度建表

用户经常会说“个人任务管理”。先判断是否真的需要独立任务表。

如果任务只是各业务模块中的负责人筛选，就优先建议：

- 不单独建总任务表。
- 在各业务表里保留负责人 / 协作人 / 状态 / 截止时间等字段。
- 通过个人视图筛选出“我的任务”。

只有当任务跨业务、跨项目、需要统一排期和复盘时，才建议单独任务表。

## 咨询流程

### 阶段一：确定业务目标和系统范围

目标：弄清楚这套多维表格要帮助用户管理什么、做出什么决策、不管什么。

优先问：

> 你希望这套多维表格主要解决什么管理问题？它需要覆盖哪些业务对象、流程或场景？

根据用户回答，继续逐个确认：

- 哪些对象是核心主数据。
- 哪些对象是过程记录。
- 哪些对象是结果 / 数据复盘。
- 哪些模块已有表格，不需要重建。
- 哪些模块只需要在仪表盘引用指标。
- 哪些模块本次不做。

### 阶段二：确定角色和权限

目标：确定不同使用者看到什么、填写什么、审批什么。

优先问：

> 这套系统的主要使用者有哪些角色？每个角色大概会在里面做什么？

常见角色类型包括：

- 管理者 / 决策者
- 业务负责人
- 一线执行者
- 数据录入者
- 审批者
- 财务 / 结算角色
- 运营 / 项目负责人
- 外部协作方 / 客户 / 供应商

要继续追问权限边界：

- 管理者是否看全局。
- 业务负责人是否只看自己负责的范围。
- 执行者是否只看自己的记录 / 待办。
- 外部协作方是否需要访问部分数据。
- 金额、合同、个人信息、绩效、审批意见、客户隐私等敏感字段是否需要限制视图。

### 阶段三：识别数据对象类型

目标：把用户口中的名词拆成可建表的数据对象，避免把角色、业务对象、流程记录和指标混在一起。

当用户列出一堆对象时，主动区分：

- 主数据：长期存在、被反复引用的对象，如客户、商品、人员、课程、资产、供应商。
- 过程记录：业务动作或流程节点，如跟进、订单、面试、入库、直播场次、课节记录。
- 明细记录：一对多的细项，如订单商品明细、费用明细、任务明细、出入库明细。
- 结果数据：复盘、绩效、销售数据、学习数据、活动数据。
- 角色 / 组织：部门、负责人、执行人、审批人、外部协作方。

如果用户列出的对象混杂，先复述你的拆分，让用户确认。只有当用户场景确实涉及内部组织和外部对象时，才使用“内部 / 外部”的拆法。

### 阶段四：决定 Base 拆分方式

目标：决定是一套 Base 多张表，还是多个 Base 分业务、分权限或分数据域管理。

必须问清楚：

> 你希望最终做成一个 Base 里的多张表，还是按业务 / 权限 / 数据域拆成多个 Base？

常见方案：

- 一个总 Base：适合权限简单、系统规模较小、强关联数据多的场景。
- 多个 Base：适合权限差异明显、业务模块相对独立、需要跨域仪表盘汇总的场景。
- 已有 Base + 新建总管理 Base：适合已有系统较多，只补缺口和总览。

用户选定后，围绕这个方案继续设计，不频繁摇摆。

### 阶段五：逐个 Base 设计表和字段

目标：把每个 Base 的表结构落到具体字段。

每次只处理一个 Base 或一张表。推荐顺序：

1. 这个 Base 的定位。
2. 这个 Base 需要几张表。
3. 每张表的字段。
4. 每个关键字段的类型。
5. 状态字段有哪些选项。
6. 哪些字段需要关联其他表。
7. 哪些字段需要汇总、公式或查找引用。
8. 哪些字段只做手动填写。

可以给候选字段清单让用户删改，但一次仍只围绕一个表或一个问题。

示例问法：

> 商品库里你们需要管理哪些基础字段？我先给一个候选清单，你删改就行。

### 阶段六：设计联动关系

目标：让表与表之间不是孤立的。

重点确认：

- 哪些表需要双向关联。
- 哪些表只需要查找引用。
- 哪些字段要从明细表汇总到月表。
- 哪些指标要从业务明细 / 角色视图汇总到管理者总览。
- 哪些字段手动填写，不做自动计算。
- 哪些字段现在不算，未来预留。

常见联动类型：

- 主数据 -> 过程记录，例如客户 -> 跟进记录、商品 -> 订单明细、人员 -> 任务记录。
- 过程记录 -> 明细记录，例如订单 -> 订单商品明细、活动 -> 报名明细、课程 -> 课节记录。
- 明细记录 -> 汇总表，例如销售明细 -> 月度销售汇总、考勤明细 -> 月度考勤汇总。
- 状态字段 -> 视图 / 自动化，例如待审批、待处理、已完成、已取消。
- 金额 / 数量字段 -> 仪表盘指标，例如应收、已收、库存、转化率、完成率。
- 已有 Base -> 新系统仪表盘，例如已有内容库只输出发布数、数据表现和状态分布。

### 阶段七：设计仪表盘

目标：明确不同角色看到哪些数据、哪些指标由底层表自动汇总。

先问最高层管理视图：

> 管理者或主要负责人打开仪表盘第一屏，最需要看到哪些指标或模块？

再确认：

- 每类角色是否有自己的仪表盘或视图。
- 总览指标是否由各业务表 / 各 Base 的数据计算而来。
- 第一屏模块排序。
- 每个模块用哪些图表或列表。
- 哪些是预警类指标。

仪表盘建议输出成模块清单，不需要过早指定复杂图表，除非用户明确要可视化样式。

### 阶段八：判断何时收束

用户可能说“差不多了”“先这样”“可以写 PRD 了”。此时不要继续追问，进入成文。

如果用户没有明确说够了，但已经确认了这些内容，也可以主动建议收束：

- 系统范围
- 角色权限
- Base 拆分
- 每个 Base 的表
- 核心字段
- 表间联动
- 仪表盘指标
- 不做事项

收束前问一个问题：

> 现在这些信息已经够写第一版 PRD 了，要不要我先沉淀成本地 Markdown？

如果用户已经明确要求最后产出 Markdown，则不用再问，直接写。

## Markdown PRD 交付

最终在当前工作目录创建本地 Markdown 文件，文件名建议：

```text
[项目名或业务名]-bitable-prd.md
```

如果项目名不清楚，用：

```text
bitable-system-prd.md
```

创建文件前，用一句话告诉用户你要写入本地 Markdown 文件。

PRD 结构优先使用 `references/prd-template.md`。根据实际项目删改，不要机械保留不相关章节。

写 PRD 时要包含：

- 文档目标
- 设计原则
- 系统范围
- Base / 应用拆分
- 每个 Base 的定位
- 每张表的字段设计
- 状态选项
- 跨表 / 跨 Base 联动
- 权限和视图设计
- 角色视图 / 角色仪表盘
- 管理者总览 / 核心看板
- 实施顺序
- 当前不做事项
- 待确认问题

交付后告诉用户：

- 文件路径
- 已覆盖哪些内容
- 哪些内容仍待确认

## 自检清单

交付前检查：

- 是否真的保持了“每次只问一个问题”。
- 是否先确认系统范围和权限，再进入字段。
- 是否尊重了用户说“已有表，不用管”的边界。
- 是否按用户业务域识别了主数据、过程记录、明细记录、结果数据和角色。
- 是否避免把公司经营管理案例硬套到其他业务域。
- 是否明确了 Base 拆分方案。
- 每张表是否有字段名、字段类型建议和说明。
- 是否写清楚关联、汇总、查找引用和手动填写的边界。
- 是否写清楚角色视图和管理者总览的关系。
- 是否把“不做事项”写进 PRD，避免后续范围膨胀。
- 是否已经创建本地 Markdown 文件，而不是只在聊天里总结。
