# 课程主编@泛函

## 使用方式

这个技能来自飞书「Agent Skill 文档库」中的同名子文档。执行任务时先读取 `references/source.md`，按原文中的步骤、质量标准、输出格式和自检清单完成工作。

如果任务涉及已有课程文稿、飞书评论、上线稿、章节改写或用户要求“直接编辑”，同时读取 `references/revision-lessons.md`。这份文件沉淀了课程评论处理、主线校准、可执行模板补全和评论闭环规则。

## 执行原则

- 先判断用户是要从零创作、优化已有材料、整理记录，还是做咨询式问答。
- 信息足够时直接推进，信息不足时只问当前最关键的 1-3 个问题。
- 保留泛函工作流的核心判断：具体、可执行、能直接进入下一步生产或交付。
- 做课程大纲时优先按“最着急的用户最快拿结果”排序，而不是按知识体系从基础到高级平铺。先识别不同紧迫程度的学习人群，再让第一、第二个模块各自交付一个可独立完成的结果。
- 用户已经给出文稿、评论、前后章节或明确要求直接编辑时，不要重新访谈；先整理已有上下文，再直接产出可用改稿或回写方案。
- 课程正文优化不是普通润色。先校准本课的教学任务和认知主线，再处理案例、结构、句子和标题。
- 课程稿不是散文诗，也不是短视频逐字稿。短句要服务口播清晰度，但不要把每个短句拆成独立段落；一个段落承载一个完整教学动作，一个句子通常由 2-5 个短句组成，用逗号、分号、冒号等连接，读起来要连续。
- 评论是编辑意图的证据。逐条判断：已吸收、待处理、与当前正文不一致、需要 CEO 判断。不要只看未解决状态，也不要机械照抄评论里的改法。
- 输出前按 `references/source.md` 和 `references/revision-lessons.md` 中的质量标准和自检清单复核。

## 成果优先课纲设计

系统课大纲不是知识目录。大纲首先要服务学习者的改变速度，尤其不能假设用户一定会学完整门课。

设计或重排大纲时，先做四个判断：

1. 识别最着急的用户是谁，他们希望多快拿到结果。
2. 判断第一模块学完后，用户能交付什么具体成果，比如公司清单、作品集、简历、触达话术、面试 pitch。
3. 判断第二模块学完后，用户能获得什么阶段性结果，比如行业地图、岗位选择、半年能力路线图。
4. 把长期认知、影响力建设、创业准备放到后置模块，作为职业复利，而不是挡在短期结果前面。

如果用户给出按人群紧迫程度划分的模块，例如“短期求职 / 半年转行 / 长期发展”，优先采用这个结构。保留原章节质量，但重排顺序，让短期行动链靠前，行业认知和长期资产后置。

课纲自检时额外检查：

- 学员只学第一个模块，是否能开始行动并拿到阶段成果？
- 学员只学前两个模块，是否已经解决了短期行动和方向选择？
- 每个模块是否有明确对象、核心问题、交付结果和下一步动作？
- 是否把“行业背景知识”放在了急需行动的人之前，导致他们来不及拿结果？

## 已有文稿精修流程

1. 读材料：正文、标题、前后章节、评论、版本/编辑时间。没有权限或接口拿不到的信息要明确说明，不要猜。
2. 定任务：判断本课是建立全景图、讲一个方法、拆一个模板、纠偏一个误区，还是给行动清单。若正文中的“核心观点”和真实教学任务冲突，优先修正教学任务。
3. 建主线：找一句能贯穿全文的强判断，让它在开头出现，中段被案例和方法解释，结尾被回收。
4. 调节段落：把同一解释链条合并成自然段。默认一个段落 1 个完整句群，1 个句群包含 2-5 个短句，屏幕上约 2-3 行；只有强调、转场、提问、例句、列表和金句回收时才单独成段。
5. 补执行：凡是出现“调研、拆解、判断、搭团队、评估”等动作，尽量补成可检查字段、步骤、标准或小公式。
6. 补边界：容易被误读的建议要写清适用条件、负责人边界和风险，尤其是招聘、投放、预算、客户承诺、价格等话题。
7. 做闭环：交付时说明改了什么、哪些评论已处理、哪些仍需 CEO 判断、是否需要回写飞书或进入 CEO 审查队列。
