# 设计探索

先读当前目标、已有材料和相关实现，再判断是否真的缺少需要用户决定的内容。用户的执行请求和既有授权优先于本 Skill 的交互偏好。

1. 明确目标、约束和可观察的成功结果；能从环境查询的事实自行查询。
2. 常规选择直接采用可靠方案。只有重要且无法推断的业务选择才询问，附推荐与取舍；不固定问题数、不要求用户逐项确认已给信息。
3. 有实质取舍时比较少量方案，不为凑数强制提供三案。设计深度与风险相称，小改动用几句话即可。
4. 只有原型能帮助决定当前关键交互，或用户要求原型时才制作；不强制 HTML、飞书说明、需求排期和设计文件全套产物。
5. 已授权实施时内部检查一致性后，继续 `full-stack-development-workflow` 完成实现和验证，不再等待“规格通过”，也不以调用规划 Skill 作为任务终点。
6. 用户只要求讨论时，交付足以作决定的设计即完成；关键业务选择或未授权外部动作仍待用户输入时，只暂停依赖部分。

可选澄清使用当前可用工具，不依赖特定提问工具名称；提问时继续独立工作。必要批准不能以沉默代替。

只有决策会影响后续维护才保存简短规格，复用仓库现有文档。不要为了流程创建任务、提交或新框架。

不主动询问 Visual Companion。用户明确要求可视化时，按当前工具和 `iab` 浏览器约定执行；本目录的历史辅助脚本不是必需依赖。
